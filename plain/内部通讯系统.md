# CCGUI 内部通讯系统设计文档

## 1. 定位

内部通讯系统是 CCGUI 的内部基础设施，负责为在线对象提供统一的注册、发现和消息投递能力。

当前第一阶段目标很明确，只包含三部分：

- 身份注册
- 对象发现
- 消息投递

它不是任务系统的一部分。任务系统只是它的上层消费者之一。

---

## 2. 设计目标

内部通讯系统第一阶段需要解决的问题：

- 一个对象如何注册到系统中
- 系统如何按项目、团队、类型发现对象
- 一个对象如何给另一个对象发送消息
- 目标忙碌时如何进入队列
- 目标不存在时如何返回失败

当前不纳入第一阶段范围：

- 持久化离线消息
- 历史消息系统
- 复杂事件总线
- 任务状态编排
- 多播/广播

---

## 3. 核心概念

### 3.1 Endpoint

所有参与内部通讯的对象都统一抽象为 endpoint。

第一阶段支持两类 endpoint：

- `agent`
- `system`

例如：

- 一个运行中的 agent session
- 某个项目下的 task 系统

### 3.2 Endpoint ID

所有 endpoint 都通过唯一 `id` 路由。

当前约定：

- agent：`session-<session_id>`
- task system：`task-<project_uuid>`

后续其他系统也遵循同样思路，例如：

- `notify-<project_uuid>`
- `review-<project_uuid>`

### 3.3 在线注册表

内部通讯系统只维护当前在线对象。

- 已连接并注册的对象，视为在线
- 断开连接后立即清理

因此第一阶段不单独维护 `online_status`。

注册表使用 endpoint `id` 作为唯一索引。

第一阶段的最小注册表结构如下：

```ts
registry[id] = {
  identity: {
    id: string,
    kind: 'system' | 'agent',
    project_id: string,
    team_id: string | null,
    role: string | null,
    work_status: 'idle' | 'busy',
    name: string
  },
  target: sessionInstance | systemHandler
}
```

说明：

- `identity` 供发现服务使用
- `target` 供消息投递使用
- agent 的 `target` 是对应的 `sessionInstance`
- system 的 `target` 是对应的内部 handler

---

## 4. 身份模型

### 4.1 Identity 结构

```ts
{
  id: string,
  kind: 'system' | 'agent',
  project_id: string,
  team_id: string | null,
  role: string | null,
  work_status: 'idle' | 'busy',
  name: string
}
```

### 4.2 字段说明

- `id`
  唯一路由 ID

- `kind`
  对象类型，当前只支持 `system` 和 `agent`

- `project_id`
  所属项目 UUID

- `team_id`
  所属团队，没有则为 `null`

- `role`
  身份角色，自定义字符串，由注册方声明

- `work_status`
  工作状态，当前只支持：
  - `idle`
  - `busy`

- `name`
  展示名称

### 4.3 说明

- `kind` 决定对象类型
- `role` 不参与路由，只是身份描述
- 不保留离线对象，所以不需要 `online_status`

---

## 5. 消息模型

### 5.1 Message 结构

```ts
{
  id: string,
  sender: string,
  receiver: string,
  message: string,
  time: string
}
```

### 5.2 字段说明

- `id`
  消息唯一 ID

- `sender`
  发送方 endpoint id

- `receiver`
  接收方 endpoint id

- `message`
  消息正文

- `time`
  消息时间

---

## 6. 核心接口

### 6.1 注册

```ts
register_identity(identity)
```

含义：

- 按 identity 结构声明并注册一个在线对象
- 主程序将其写入内存注册表
- 同时记录对应的 `target`
- bridge 启动后的初始化内容就是一份完整的 identity 数据

返回值：

```ts
{ ok: true }
```

规则：

- 同一个 bridge 连接只允许注册一个 identity
- 同一个 `id` 重复注册时，新注册覆盖旧注册
- 注册成功后，该 identity 立即可被发现服务返回

### 6.2 注销

```ts
unregister_identity(id)
```

含义：

- 按 id 注销对象
- 连接断开时也应自动触发清理
- 清理时直接删除注册表项

返回值：

```ts
{ ok: true }
```

### 6.3 发现

```ts
discover_identities({
  project_id?,
  team_id?,
  kind?
})
```

支持的发现维度：

- 按项目发现
- 按团队发现
- 按 kind 发现

返回：

- 匹配到的 identity 列表

实现方式：

- 直接遍历注册表
- 对每项的 `identity` 做过滤
- 返回符合条件的 identity

过滤规则：

- 所有已传入的筛选字段之间是 AND 关系
- 未传入的字段表示不参与过滤
- `team_id: null` 可用于筛选无团队对象

返回顺序：

- 第一阶段不保证固定排序

### 6.4 发送消息

```ts
send_message(message)
```

其中 `message` 使用前面定义的消息结构。

额外规则：

- `sender` 必须存在于注册表中
- `receiver` 必须是合法 endpoint id
- `message.id` 由调用方提供，主程序不改写
- `message.time` 由调用方提供，主程序不改写
- `message.message` 不能为空字符串

---

## 7. send_message 返回值

第一阶段最小返回值如下：

```ts
{
  status: 'delivered' | 'queued' | 'not_found' | 'deny_self_send',
  message_id: string
}
```

如果请求体不合法，接口应直接返回错误，而不是复用上述状态值。

### 7.1 状态说明

- `delivered`
  投递成功，目标当前空闲，已直接送达

- `queued`
  投递成功，目标当前忙碌，已进入队列

- `not_found`
  投递失败，目标不存在

- `deny_self_send`
  投递失败，不允许给自己发消息

---

## 8. 投递规则

第一阶段投递规则保持简单：

- 如果 `sender === receiver`，返回 `deny_self_send`
- 如果 `receiver` 不存在，返回 `not_found`
- 如果 `receiver.work_status === 'idle'`，直接投递，返回 `delivered`
- 如果 `receiver.work_status === 'busy'`，进入目标队列，返回 `queued`

投递流程：

1. 按 `receiver` 查注册表
2. 如果 `sender === receiver`，返回 `deny_self_send`
3. 找不到则返回 `not_found`
4. 找到后读取该项的 `target`
5. 如果目标空闲，直接通过 `target` 投递
6. 如果目标忙碌，写入该目标的 FIFO 队列

当前只要求最小队列能力：

- 每个 receiver 有自己的待投递队列
- 队列策略使用 FIFO
- 同一 receiver 同时只处理一条消息

### 8.1 agent 消息接收

发送消息走 MCP。

但 agent 接收消息时，不通过 MCP 反向推送，而是由 CCGUI 主程序先通过 `sessionInstance` 或 `sessionManager` 向前端 UI 发送专门通知，再由 UI 复用现有发送流程完成投递。

也就是：

- agent 发消息：通过 MCP `send_message`
- agent 收消息：CCGUI 先通知前端 UI
- UI 再复用现有 `sendMessage`
- 接收侧表现为一种特殊用户消息

这样做的原因是：

- 保留现有可视化发送路径
- 保留前端对忙碌状态和发送流程的控制
- 避免主程序单独维护另一套消息注入逻辑

主程序发给前端的最小内部通知结构建议为：

```ts
{
  receiver_id: string,
  message: {
    id: string,
    sender: string,
    receiver: string,
    message: string,
    time: string
  }
}
```

前端收到后：

- 根据 `receiver_id` 定位目标 session
- 将该消息作为特殊用户消息注入现有发送流程
- UI 侧需要保留原始 `sender`

### 8.2 system 消息接收

system 类型目标不经过 MCP。

消息到达后，CCGUI 直接调用注册表中对应的内部 handler。

system 类型 `target` 需要提供统一入口，例如：

```ts
handleMessage(message)
```

### 8.3 busy 队列出队

由于 agent 消息的最终发送由前端 UI 完成，因此 busy 队列的出队也由现有发送流程结束来驱动。

第一阶段建议规则：

- 主程序判断目标 busy 时，将消息写入该目标 FIFO 队列
- 当前这条消息在前端发送流程结束后
- 主程序再通知前端继续发送下一条

也就是：

- 主程序负责排队和调度
- 前端负责真正执行发送

前端发送流程结束后，需要向主程序发回一个内部完成通知。

最小事件结构建议为：

```ts
{
  receiver_id: string,
  message_id: string
}
```

主程序收到后：

1. 将该 receiver 标记为可继续投递
2. 检查该 receiver 的 FIFO 队列
3. 若存在下一条消息，则继续通知前端发送

### 8.4 work_status 维护

第一阶段建议由主程序结合发送流程维护 `work_status`。

规则：

- 某个 receiver 开始处理消息时，置为 `busy`
- 当前消息发送流程结束后，若队列为空，则置为 `idle`
- 当前消息发送流程结束后，若队列非空，则继续保持 `busy`

第一阶段不依赖 agent 主动上报 `work_status`

## 9. 与任务系统的关系

任务系统未来会作为一个 system endpoint 接入。

当前约定：

- task 系统 endpoint id：`task-<project_uuid>`
- system endpoint 在项目打开时注册
- 项目关闭时注销对应 system endpoint

这样同项目中的 agent 就可以直接向任务系统发送消息，例如：

- 某个 agent 向 `task-<project_uuid>` 汇报结果
- 某个 system 向指定 agent 下发任务消息

内部通讯系统只负责路由，不负责解释 task 语义。

---

## 10. bridge 与连接生命周期

### 10.1 bridge 角色

bridge 是一个纯透传程序，只负责：

1. 读取启动参数中的 unix socket 地址
2. 将 identity 数据发送给主程序完成注册
3. 在 agent 与 CCGUI 之间透明转发 MCP 数据

bridge 不承载业务语义。

### 10.2 初始化包

bridge 建立 unix socket 连接后，第一包固定为注册包：

```json
{
  "type": "register_identity",
  "identity": {
    "id": "session-xxx",
    "kind": "agent",
    "project_id": "project-uuid",
    "team_id": "team-1",
    "role": "developer",
    "work_status": "idle",
    "name": "Agent A"
  }
}
```

### 10.3 传输格式

第一阶段建议主程序与 bridge 之间使用：

- newline-delimited JSON

也就是每个协议包占一行 JSON。

### 10.4 连接生命周期

规则：

- 一个 bridge 连接只对应一个 identity
- bridge 连接建立后先注册 identity，再进入透明转发
- bridge 连接断开时，主程序立即删除对应注册表项
- 若该 identity 有未处理队列，第一阶段直接丢弃，不做离线保留

---

## 11. 当前结论

第一阶段内部通讯系统的核心已经收敛为：

- 统一 endpoint 模型
- 统一 identity 结构
- 统一 message 结构
- 注册 / 注销 / 发现 / 发送消息 四个基础接口
- `delivered / queued / not_found / deny_self_send` 四种投递结果
- 注册表直接保存 `identity + target`
- agent 接收消息由主程序调度、前端执行发送
- bridge 只负责初始化注册和透明转发

这版定义已经足够支撑后续架构讨论和最小实现。
